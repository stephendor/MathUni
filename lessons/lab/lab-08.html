Mapper (lab-08)

Three hundred points on a circle. One hole. Mapper's answer depends on four choices, and two of them appear nowhere in its definition. Across twenty reasonable cover settings the graph reports one hole in eight. Holding the cover fixed and changing only the lens turns one hole into six. Holding everything fixed and swapping the library changes the answer from one to none. lab-05 gave persistence a stability theorem that converts an error bound on the data into an error bound on the summary; Mapper has a theorem too, and every hypothesis it needs is one a point cloud does not have. This unit is about reporting an object honestly when nothing guarantees it.

Predict before we start. Mapper is defined as the nerve of the pullback cover of a map f : X → Z. What does a Mapper implementation need that the definition does not mention?

A clusterer. Definition 9.4 decomposes each f⁻¹(U_α) into its path connected components, and a finite point cloud carries the discrete topology, in which every component is a single point. So every implementation substitutes a clustering algorithm — and its parameters are choices with no counterpart in the definition. DBSCAN(eps=0.30, min_samples=3) is used throughout this lesson, and min_samples in particular can discard points entirely, which nothing in the book does. The second option names a real ingredient — the point-cloud construction on printed 270 does use a distance — but the metric is data, not a missing piece of the definition.

Why this matters for the mission: Mapper's graph is a topological summary; its clustering leans on la-15's spectral machinery.

The strip's first clause needs bounding and its second clause is wrong on both halves. This one needs a syllabus edit.

"A topological summary" — true, and of what? Mapper is the nerve of a pullback cover (Definition 9.4, printed 269), so it summarises the topology of a cover, and the cover is chosen. Remark 9.1 on the same page records that one choice makes it a merge tree and another makes it a relaxed Reeb graph — different kinds of object, one of which cannot have a loop at all. Measured here: 8 of 20 cover settings recover the circle's single hole; the radial lens reports six; two libraries disagree about whether there is one or none. The clause is right and the article is not: there is no "the" Mapper graph of a dataset.

"Its clustering leans on la-15's spectral machinery" — no. Two separate faults. First, la-15 is Spectral theorem (real case), sourced to Axler 7A–7B, and it is unwritten — the la module has only la-01 and la-02 on disk. Second, and independently of that: the spectral theorem for real symmetric operators is not what a Mapper clusterer uses. Mapper's clusterer is a free choice, the one executed throughout this lesson is DBSCAN, which is density-based and computes no eigenvector of anything, and even spectral clustering — a different construction, resting on the graph Laplacian — is only one option among many. For the syllabus pass: the second clause should be struck or rewritten to say that the clusterer is a free choice with no counterpart in Definition 9.4. That is the true and load-bearing statement, and it is what this unit teaches.

Not claimed here. That Mapper is unreliable or should not be used — it is a genuinely useful exploratory tool and the module says so. What is claimed is that its output is a function of four stated choices, and that a report omitting them has not specified its own figure.
Segment 1 · 25 min

The definition, and the ingredient it does not mention

Definition 9.4 (Mapper), printed 269. Let X and Z be topological spaces and let f : X → Z be a well-behaved and continuous map. Let 𝒰 = {Uα} be a finite open cover of Z. The mapper arising from these data is defined to be the nerve of the pullback cover f*(𝒰) of X; that is, M(𝒰, f) := N(f*(𝒰)). Defined, printed 269, after the pullback cover is constructed on printed 268 by decomposing each f⁻¹(Uα) into its path connected components. "Well behaved" is defined on 268 to mean that every path connected open U has finitely many path components in its preimage.

Match that against a call. X is a 300-point cloud; Z is ℝ; f is Projection(columns=[0]); 𝒰 is CubicalCover(n_intervals=10, overlap_frac=0.30). Four ingredients, four arguments — except the call takes a fifth.

Worked — the fifth argument, and what it replaces.

clusterer=DBSCAN(eps=0.30, min_samples=3). Definition 9.4 asks for path connected components of f⁻¹(Uα). A finite point cloud has the discrete topology, in which every path component is a single point, so Definition 9.4 applied literally to a point cloud returns a graph with 300 nodes and no edges. The clusterer is what stands in.

Dey and Wang supply the substitute themselves, on printed 270: build Gr(P) with an edge whenever d(p, p′) ≤ r, and take the components of the subgraph spanned by each interval's points. That is single-linkage at threshold r.

DBSCAN is not that, and the difference matters. With min_samples=1 DBSCAN reduces exactly to single-linkage at eps. With min_samples=3 it separates core points, border points and noise — and noise points join no cluster, so they disappear from the summary. Nothing in the book discards data. A parameter that can delete points from a topological summary has no counterpart in Definition 9.4 or in the point-cloud construction, and it is on by default.

Self-check 1. Dey and Wang write that "in the limit that each interval degenerates to a point, the discretized Reeb graph converges to the original Reeb graph as shown in [132, 241]". What does that license?

An asymptotic claim, and one weaker in three ways than lab-02's Nerve Theorem: that was a theorem in the source, with hypotheses you could check (closed convex sets), and lab-02 could therefore state exactly what Čech carried and Rips did not. This is a citation to absent papers about a limit that no finite cover reaches. The first option is the overreach the sentence invites — "converges in the limit" says nothing about any particular cover, and Segment 2's table shows the finest cover in the sweep is the only one that never works.
Faded — the article in "the Mapper graph".

Remark 9.1 (printed 269) records that the construction is general enough to encompass both merge trees and Reeb graphs, depending only on which cover of ℝ you take: sublevel sets Uα = (−∞, α) give merge trees; ε-thick level sets Uα = (α − ε, α + ε) give a relaxed Reeb graph.

A merge tree is a tree. It has no loops, ever. A Reeb graph can have many.

Segment 2 · 30 min

A theorem about cycles, and a sweep that is not a test of it

Theorem 9.16(a), printed 274. Let f : X → Z be a map from a path connected space X to a metric space Z equipped with a cover 𝒰, and let 𝒰′ be the restriction of 𝒰 to f(X). Let z₁, …, z_g be an optimal cycle basis for H₁(X) in the pullback metric. Let ℓ = g + 1 if λ(𝒰′) > s(z_g); otherwise let ℓ be the smallest integer with s(z_ℓ) > λ(𝒰′). If ℓ ≠ 1, the class φ𝒰*[z_j] = 0 for j = 1, …, ℓ − 1. Moreover, if ℓ ≠ g + 1, the classes {φ𝒰*[z_j]} for j = ℓ, …, g generate H₁(N(f*𝒰)). Stated and derived from Theorem 9.10 earlier in the chapter, printed 274. It rests on Definition 9.6 (the pullback pseudometric d_f, printed 273) — the metric in which the cycle sizes s(z) are measured — and on Proposition 9.15 (printed 273, proved), which says the pullback cover has the same Lebesgue number as 𝒰′.

In words: cycles smaller than the cover's Lebesgue number are killed; the survivors generate. The cover decides which loops you see. So sweep the cover.

Twenty covers, one circle, one benchmark. Green is b₁ = 1, matching the loop the cloud was built from; grey is b₁ = 0. The benchmark exists only because the cloud is synthetic: no theorem here obliges a Mapper graph to recover it, so a green cell is evidence about those parameters and not a certificate. Each cell also carries k, the number of connected components of the graph. Eight of twenty are green, and they form a band that needs more overlap the more intervals you use. Read the k column on the left: at 25 intervals and 5% overlap the graph has 46 nodes, 11 edges and 35 components — it has not lost a loop, it has fallen apart. And note the bottom row: the finest cover in the sweep is the only one that never works.

Self-check 2. The whole 5% column reports b₁ = 0, with 3, 5, 7, 16 and 35 components. Does Theorem 9.16 predict that?

No. b₁ = e − v + k, and at 25 intervals with 5% overlap that is 11 − 46 + 35 = 0 — the loop was never closed, not killed. The nerve has an edge only where two cover elements meet, and at 5% overlap they barely do. Theorem 9.16 presupposes a genuine cover of a path connected space and describes which classes of H₁(X) die under it; a cover of a finite point set whose pieces do not meet is not modelling an open cover of the circle at all. This is the distinction the problem set presses: losing a feature and never building the object look identical in the output and are different failures.
Guided — why the finest cover is the one that never works.

Theorem 9.16 reads naturally as "shrink the cover and only small cycles die, so a fine cover keeps everything". The bottom row of the grid says the opposite: 25 intervals gives b₁ = 0 at every overlap tested, including 0.45 where 15 intervals succeeds. Before reading on: write down (i) what "shrink the cover" means in the theorem, (ii) what it additionally does in the implementation, and (iii) why those are not the same quantity.
The two parameters that move together (i) In the theorem, shrinking the cover means reducing the Lebesgue number λ(𝒰′) of an open cover of Z, holding the covering property fixed. The consequence is exactly as advertised: the threshold s(z) > λ falls, so fewer cycles are killed.

(ii) In the implementation, shrinking the intervals also reduces the number of points in each one. At 25 intervals over the same range there are roughly twelve of the 300 points per interval, spread over a thin band, and DBSCAN fragments them — 46 nodes in 3 to 35 components depending on overlap.

(iii) They are not the same quantity because the theorem's X is a path connected space where "smaller cover element" costs nothing, and the implementation's X is a sample, where a smaller cover element means fewer points and eventually too few to be connected by any clusterer. The implementation has a failure mode — sparsity — with no counterpart in the theorem, and it runs in the opposite direction to the theorem's own parameter. Anyone reasoning from Theorem 9.16 to "use a fine cover" will walk straight into it.

Self-check 3. Which of Theorem 9.16's hypotheses does the sweep satisfy non-vacuously?

One of four. X path connected: no — 300 isolated points. f continuous: true on a discrete space for every f, and therefore says nothing. f well behaved: also vacuous, and in the worst way — every preimage has as many path components as it has points, which is finite, so the condition holds while its intent fails completely. 𝒰 an open cover of a metric space: yes, of ℝ. The third option is wrong twice over: a finite metric space is a topological space — it carries the discrete topology — and in any case the cover 𝒰 lives in ℝ, not in X. Having a topology is not the problem; having that topology is, since in it every point is its own path component. So the sweep is evidence about the software's behaviour, and about the qualitative claim that Mapper's output is a function of its parameters. It is not a test of Theorem 9.16, which says nothing about any object in this lesson. The third option overstates: a finite set is a perfectly good topological space, just a discrete one, and that is precisely the problem.

The lens, and two libraries that disagree

Worked — one hole becomes six. Same cloud, same cover, same clusterer. Only the lens changes.

The radial lens has destroyed the structure before any topology is computed. On a unit circle with noise 0.05, the distance from the origin ranges over roughly [0.85, 1.15] rather than over [−1, 1] — so the ten intervals subdivide the noise. Each interval's preimage is a scattered set of points from all round the circle, DBSCAN splits it into several clusters, and the nerve wires those together by accidents of which noisy points share an interval. Six loops, none of them in the data, all of them dependent on the seed.

Definition 9.6 (printed 273) is why this is not a cosmetic choice. The pullback pseudometric is d_f(x, x′) := inf over paths γ of diamZ(f ∘ γ), and Theorem 9.16's cycle sizes s(z) are measured in it. Changing f changes the metric in which cycles count as small — so the lens is part of the object the theorem is about, not a viewing angle on it.

Self-check 4. Proposition 9.15 says the pullback cover f*𝒰 has the same Lebesgue number as 𝒰′. Does that rescue the radial lens?

No, and the proposition is what makes the failure legible. It does buy something real: you set λ by choosing intervals in Z and get the same λ on X for free, so you can reason downstairs. But λ lives in the pullback pseudometric, and under the radial lens two points on opposite sides of the circle have almost the same f-value — so a path between them has small diam(f ∘ γ) and d_f collapses. The cover is fine in ℝ and useless on X. Proposition 9.15 transmits the number faithfully; it does not make the number mean what you wanted.

Same cloud, same lens, same clusterer, same nominal cover parameters — and at n = 15, overlap 0.45 the two libraries disagree about b₁ itself.

Disagreement here is expected, and this experiment does not tell you whether either has a bug. Definition 9.4 leaves genuine freedom: where the outer intervals' endpoints sit, whether the overlap fraction is measured against the interval width or the gap, which side a boundary point goes, whether an empty cluster becomes a node. Kepler-Mapper reports 26 nodes where giotto-tda reports 28 — exactly two fewer, consistent with two end clusters not being formed.

Be careful about the step past that. This lesson said "neither has a bug" in draft, reasoning that both compute the nerve of a pullback cover. Neither quite does. Definition 9.4 takes path-connected components of f⁻¹(Uα); both pipelines substitute DBSCAN, which at min_samples=3 throws points away as noise, so the clusters need not cover f−1(Uα) and are not a pullback cover in the definition's sense. Two heuristics can differ because the definition underdetermines them or because one is defective, and separating those would mean comparing interval endpoints, point assignments, noise handling, clusters and edges — none of which is done here.

Contrast lab-03, where an independent implementation agreed, and where disagreement would have meant a bug, because the barcode is unique by a theorem. Here there is no such theorem, so the disagreement is uninformative in both directions: it convicts nobody and it clears nobody.

Self-check 5. CubicalCover's default overlap is 0.1; kmapper.Cover's is 0.5. On this data, what do the two defaults give?

Opposite answers, and both are run rather than read off the grid. giotto-tda's default gives 18 nodes, 15 edges, b₁ = 0 — wrong. Kepler-Mapper's gives 16 nodes, 16 edges, b₁ = 1 — right — out of the box, silently, on identical data.

Reading them off the grid would have been a mistake worth noticing: overlap_frac and perc_overlap are not the same quantity, so one library's column is not evidence about the other's default, and Kepler-Mapper's 16/16 is a row that appears nowhere in the sweep. This is the discipline lab-01 derived for library defaults and lab-02 for filtration conventions, arriving here in its sharpest form: never report a Mapper graph without its cover parameters, because the defaults do not agree and one of them is wrong here.
